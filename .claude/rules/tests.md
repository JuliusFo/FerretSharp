# Tests

- **xUnit v3** auf der **Microsoft Testing Platform** + NSubstitute. Kein VSTest: `Microsoft.NET.Test.Sdk` und `xunit.runner.visualstudio` nicht verwenden.
- Unit-Tests laufen ohne DB (Mocks/Fakes). Alles, was eine echte DB braucht, gehört in `FerretSharp.Integration.Tests` (Testcontainers.Oracle, `gvenzl/oracle-free:23-slim-faststart`) und muss sich ohne Docker sauber überspringen. Teile, die die .NET-8-Runtime brauchen (ModelHost, `FakeEfApp`), ebenso: Pfade dorthin über `Net8.Require`, der Container-Start fängt jeden Fehler (`OracleContainerFixture`) – Skip mit Grund, Tests ohne DB laufen weiter. In der CI (`CI=true`) überspringt nur ein fehlendes Docker, alles andere scheitert. Eine Testklasse, die in `InitializeAsync` überspringt, prüft im `DisposeAsync` auf null.
- Reine JavaScript-Module (Rechnung ohne DOM, z. B. `gridSelection.js`) haben Tests in `tests/js/*.test.mjs` mit `node:test` (ADR 0031): keine npm-Pakete, `dotnet test` startet sie (`JsTests`), ohne Node übersprungen, in der CI ein Fehler.
- Ordner nur über `TestFolder` (`tests/Shared`) anlegen und löschen, nie selbst rekursiv löschen (`SafeDeleteTests` durchsucht auch die Tests).
- Die Tests laufen mit deutscher UI-Kultur (`tests/Shared/UiCulture.cs`), damit ältere Tests ihre deutschen Texte prüfen; englische Texte mit `using (UiCulture.Use("en")) { … }`. Zahlen in Texten (`{0:N0}`) folgen dagegen der Kultur der Maschine, nicht der UI-Kultur: „10.000“ lokal, „10,000“ in der Linux-CI – die erwartete Zahl mit `ToString("N0", CultureInfo.CurrentCulture)` bauen (WP-59, CI rot). `ResourceTests` (Core, UI) prüfen beide Sprachen je Schlüssel.
- Stand-ins: `FakeModelHost` (Prozessweg des ModelHost, Szenario per `--scenario`), `FakeEfApp` (App mit EF Core 8, an die sich die Integration.Tests für „Statements der App“ hängen), `FakeEfModel` (Contexts mit eigenem Connection-String für die LINQ-Konsole).
- Coverage (`tests/coverage.config`): Ein Kindprozess, der eine eigene Kopie von `FerretSharp.Core`/`UI`/`AppTrace` lädt (heute der `FakeModelHost`), muss per `ModulePaths`/`Exclude` aus der Messung. Sonst überschreibt er unter Linux die Treffer des Testprozesses: Die CI verlor so von R4b bis 3.34.0 je Lauf einen anderen Teil der Core-Abdeckung (Badge rund 74 % statt 88 %), lokal unter Windows fiel es nicht auf. Ein Abfall des Badges ohne neuen ungetesteten Code: erst lokal mit `tools/coverage/Get-Coverage.ps1` vergleichen.
- Zeit über `TimeProvider` (`FakeTimeProvider`), nicht mit festen `Task.Delay` abwarten. Mischt ein Test die falsche Uhr mit echten Ereignissen (Dateien beim `BuildOutputWatcher`): erst auf das Ereignis warten (`Seen`/`Handled`), dann vorspulen, bis gemeldet wurde (`Reported`) – ein späteres Ereignis desselben Schreibvorgangs kann das Ende der Ruhezeit verschieben, während die Uhr läuft; ein einzelnes `Advance` meldet dann nie. Vorspulen auf einem Pool-Thread (`Task.Run`), wenn der Callback weiterläuft wie mit der Systemuhr. Wartet der Code nach einem Ereignis erneut (`Task.Delay(…, time, …)` in einer Schleife), erst vorspulen, wenn der neue Timer angelegt ist – sonst verpufft `Advance` (so flackerte `SessionWatchTests` unter Last): eine Unterklasse von `FakeTimeProvider` zählt die Aufrufe von `CreateTimer`.
- Das Token, das ein Callback über `OracleSession.RunAsync` bekommt (`onBlock` des Exports, `read` eines Readers), ist das eigene der Session und wird auf einem Pool-Thread abgebrochen (A3) – es folgt dem Token des Aufrufers einen Moment später. Ein Test, der abbricht und sofort `ct.ThrowIfCancellationRequested()` erwartet, rennt gegen diesen Thread (so scheiterte `A_whole_read_cancelled_in_the_middle_…` in der CI nach 3.45.0); stattdessen auf `ct` warten (`Task.Delay(…, ct)`).
- Ein Fake merkt einen Abbruch nicht über `ct.Register(…)`, wenn er auch selbst auf das Token wartet (`WaitToReadAsync(ct)`): Callbacks laufen in umgekehrter Reihenfolge, das Warten endet zuerst, und die Schleife kann die eigene Registrierung entsorgen, bevor ihr Callback lief – der Callback läuft dann nie (so flackerte `AppTraceServiceTests.Detaching_…` unter Last). Stattdessen am Ende `ct.IsCancellationRequested` lesen, auf dieses Ende wartet der Code. Nachstellen: eine zweite Registrierung ohne `using`, die schläft (verbreitert das Fenster).

## UI.Tests
- Prüfen die State-Klassen ohne Rendern: `TestApp` verdrahtet Hub, Scopes und Fakes; `FakeDataEditor` spielt Schreiben, Undo/Redo, Commit, DDL und auf Wunsch Konflikte und gescheiterte Rollbacks, `TestApp.ReadSql` den Leseweg. Beide lehnen ab wie die Session (`StatementGuard`; DDL nicht, solange seit Commit/Rollback geschrieben wurde – Review 3.40.0, C1). `TestApp.Profile` macht Prod wie die App schreibgeschützt: Der Workspace ist gesperrt, der Fake verweigert dann wie Oracle (`FakeDataEditor.ReadOnly`); ein Test, der auf Prod schreibt, entsperrt vorher (`UnlockAsync`). Die Datenbankseite ohne `TestApp` baut `FakeDatabase`; `InMemorySecretStore`, `InMemoryWorkspaceStore`, `Repository`, `ReleaseWorkflow` liegen ebenfalls in `tests/Shared` (Namespace `FerretSharp.Testing`, je Testprojekt verlinkt). Tests liegen im Ordner des Bereichs, den sie prüfen (R6b, C10).
- Es gibt keinen Dispatcher wie Blazors UI-Thread: Die Session eines Workspaces öffnet beim ersten Zugriff per `Task.Run`, alles danach läuft auf dem Threadpool weiter. Ein Test, der eine Aktion startet, ohne sie abzuwarten, und dann einen Fake umstellt (`OnCommit`, `ReadSql`), wartet vorher auf ein Signal aus dem Fake („angekommen“) – sonst greift der Halt nicht, und zwei Aktionen laufen gleichzeitig über Zustand, den die App nur vom UI-Thread anfasst (so flackerte `A_running_commit_blocks_only_its_own_workspace`).
- Auf etwas warten, das ein anderer Thread wahr macht: `Wait.UntilAsync(…, what)` (`tests/Shared`), keine eigene Schleife (Review 3.54.0, C11: acht Kopien). Eine Auto-Property eines NSubstitute-Fakes (`session.Data`), die Test- und Pool-Thread zugleich zum ersten Mal lesen, liefert zwei verschiedene Instanzen – im Test vorher fest setzen (`fix-session-open-retry`).
- `ConnectionServiceInjectionTests` schlägt bei `[Inject]` eines verbindungsgebundenen Dienstes an, `SettingsCatalogTests` bei einem `SettingKey` ohne Eintrag.

## Redundante Tests
Jeder Test kostet Laufzeit und Pflege; ein neuer Test muss einen Fehler fangen, den kein anderer fängt. Vor dem Schreiben prüfen:
- Gleicher Aufbau, nur ein anderer Wert → ein Fall mehr im bestehenden `[Theory]`, kein neuer `[Fact]`.
- Prüft die Schicht darunter denselben Fehler schon (Core-Test für eine Regel, die die State-Klasse nur weiterreicht), testet der neue Test nur, was die obere Schicht selbst entscheidet.
- Kein Test für Sprache oder Bibliothek (Record-Gleichheit, Setter, Standardverhalten von `System.Text.Json`) und keiner, dessen Assert nicht scheitern kann.
- Nie weg: Tests, die einen Review-Befund oder Bugfix festhalten, und die Invarianten-Tests (`ReadOnlyTests`, `SafeDeleteTests`, `ArchitectureTests`, `ResourceTests`) – außer ein anderer Test fängt genau denselben Fehler.

Das Gesamt-Review (`/complete-code-review`, Agent TE) sucht überflüssige Tests; nach dem Trimmen kommen hier die Learnings dazu: was die entfernten oder zusammengelegten Tests überflüssig machte, als Regel für neue Tests, je mit einem Beispiel (Testname, Review).
- **Eine Einstellung bekommt keinen eigenen Test für Standard und Round-Trip.** Zehn Tests „alte Datei → Standard → speichern → laden“, je Einstellung einer, prüften Property-Initialisierer und `System.Text.Json`; jede neue Einstellung brachte eine Kopie. `SettingsStoreTests.An_old_file_gives_every_setting_it_does_not_name_its_default` und `Every_setting_round_trips` (setzt jede Property per Reflexion vom Standard weg; ohne Wert für einen neuen Typ scheitert er) fangen beides für alle, auch künftige (Review 3.54.0, C13). Die Werte der Standards sind Entscheidungen des Nutzers und stehen in **einem** Test (`A_missing_file_gives_the_decided_defaults`) – beim Zusammenlegen gingen sie zuerst verloren (Review von R8).
- **Vor dem Zusammenlegen jeden Assert der alten Tests abhaken:** Was nur ein alter Test prüfte (hier die konkreten Standardwerte), braucht einen Platz im neuen; die Gegenprobe zeigt das nicht, wenn man nur die Fehler bricht, an die man gedacht hat.
- **Gleicher Aufruf, andere Eingabe → ein Fall im `[Theory]`.** Sieben `[Fact]` in `SqlResultOrderTests` bestanden nur aus `Assert.Equal(expected, Sorted(sql, cols, sort))`; jetzt `One_key_goes_in_front_of_the_query_s_own_order_or_after_the_query` mit denselben Fällen (Review 3.54.0, C14). Der Name sagt die Regel, die Fälle stehen im Kommentar.
- **Behalten, obwohl ähnlich:** ein Test, der einen Bugfix auf einem anderen Weg hält (`ColumnValueCopiesTests.A_result_counts_its_null_rows`: alle Werte, blockweise – kein Core-Test geht diesen Weg).
